  <name>Task 1: Mutation counter and upload guard middleware</name>
  <files>
    packages/core/src/plugins/core-plugins/demo-sandbox/middleware.ts

  <action>
    Create `packages/core/src/plugins/core-plugins/demo-sandbox/middleware.ts` with two middleware functions:

    **CRITICAL: Demo user detection via KV key, NOT role check.**

    The `viewer` role is shared by API token users (auth.ts line 185) and standard registered users (schema DEFAULT). Checking `user.role !== 'viewer'` would incorrectly rate-limit those users. Instead, detect demo users by checking if their KV counter key EXISTS:

    Detection pattern (use in BOTH guards):
    ```typescript
    const user = c.get('user')
    if (!user) return next()  // No user = no guard

    const kv = c.env.CACHE_KV
    if (!kv) return next()  // No KV = degrade gracefully

    const kvKey = `demo-mutations:${user.userId}`
    const counterValue = await kv.get(kvKey)
    if (counterValue === null) return next()  // Key doesn't exist = NOT a demo user, skip
    ```

    The `demo-service.ts` from Plan 01 always seeds this KV key on demo signup (`demo-mutations:{userId}` -> '0' with TTL 86400). If the key does NOT exist, the user is not a demo user and should pass through unimpeded.

    **1. `demoMutationGuard` middleware:**
    - Use the KV key existence check above to identify demo users
    - Check `c.req.method` — only count POST, PUT, PATCH, DELETE. Skip GET/HEAD/OPTIONS via `next()`
    - Parse counter: `const count = parseInt(counterValue, 10) || 0`
    - If count >= 50, return `c.json({ error: 'You have reached the demo limit of 50 changes. Start a new demo session to continue.' }, 429)`
    - Otherwise, increment: `kv.put(kvKey, String(count + 1), { expirationTtl: 86400 })`
    - Set response header `X-Demo-Mutations-Remaining: {49 - count}`
    - Call `next()`

    **2. `demoUploadGuard` middleware:**
    - Use the same KV key existence check to identify demo users (NOT role check)
    - Only apply to POST requests (uploads). If method !== 'POST', call `next()`
    - Parse formData: `const formData = await c.req.formData()`
    - Get file: `const file = formData.get('file') as File | null`
    - If no file, call `next()` (let downstream handle the error)
    - Check `file.type.startsWith('image/')` — if not, return `c.json({ error: 'Demo accounts can only upload images.' }, 400)`
    - Check `file.size > 2 * 1024 * 1024` — if over, return `c.json({ error: 'Demo image uploads are limited to 2 MB.' }, 400)`
    - **Critical Hono caveat:** `c.req.formData()` consumes the request body. The downstream `api-media.ts` route also calls `c.req.formData()`. To avoid the double-consumption issue, store the parsed formData on the context: `c.set('parsedFormData', formData)`. This requires updating api-media.ts in Task 2.
    - Call `next()`

    Import types from Hono: `Context`, `Next`. Import Bindings/Variables types from `../../../app`.
  </action>
  <verify>
    - `pnpm build` succeeds
    - Both `demoMutationGuard` and `demoUploadGuard` are exported
    - `grep "role" packages/core/src/plugins/core-plugins/demo-sandbox/middleware.ts` returns NO matches (role check must not appear)
    - `grep "demo-mutations" packages/core/src/plugins/core-plugins/demo-sandbox/middleware.ts` confirms KV key pattern used
  </verify>
  <done>
    - Mutation guard detects demo users via KV key existence (`demo-mutations:{userId}`), NOT via role check

    - Upload guard validates image type and 2MB size for demo users only

    **1. Wire middleware in app.ts (NOT in the plugin index):**

    The mutation guard and upload guard need to run on existing API routes (`/api/content/*` and `/api/media/*`), not on plugin-specific routes. The cleanest approach is to apply them as global middleware in `app.ts` after auth middleware but before route handlers.

    In `packages/core/src/app.ts`, after the existing auth/CSRF middleware setup and BEFORE the route mounting:
    - Import `demoMutationGuard` and `demoUploadGuard` from `./plugins/core-plugins/demo-sandbox/middleware`
    - Apply mutation guard to content API routes: `app.use('/api/content/*', demoMutationGuard())`
    - Apply mutation guard to media routes: `app.use('/api/media/*', demoMutationGuard())`
    - Apply upload guard specifically to media upload: `app.use('/api/media/upload', demoUploadGuard())`

    Check how existing middleware (like `requireAuth`, `csrfProtection`) is applied in app.ts and follow the same pattern. The middleware must run AFTER `requireAuth` (needs user on context) and BEFORE the route handlers.

    **2. Update the Variables interface in app.ts (REQUIRED):**

    Add `parsedFormData?: FormData` to the `Variables` interface in `packages/core/src/app.ts` (around line 83). This is NOT optional — TypeScript WILL error on `c.set('parsedFormData', formData)` and `c.get('parsedFormData')` without it. The Variables interface currently has `user`, `apiToken`, `requestId`, `startTime`, `appVersion`, `csrfToken` — add `parsedFormData` alongside them:
    ```typescript
    parsedFormData?: FormData
    ```

    **3. Update api-media.ts for formData context variable:**

    In `packages/core/src/routes/api-media.ts`, in the `POST /upload` handler:
    - Before the existing `const formData = await c.req.formData()` line, replace with:
      ```typescript
      const formData = c.get('parsedFormData') as FormData ?? await c.req.formData()
      ```
    - This way, if the demo upload guard already parsed the body, reuse it. Otherwise, parse normally (for admin/editor users who skip the guard).
